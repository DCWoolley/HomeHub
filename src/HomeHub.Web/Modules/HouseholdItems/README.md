# Household Items

Current household account members share a Household Items Catalogue at `/HouseholdItems`, accessible from household navigation. This is for non-food consumables and is separate from Ingredients and recipes.

Members can add, list, rename, and change the default usage unit of an item. Names and unit labels are trimmed, with maximum lengths of 100 and 50 characters respectively. Names are unique within the household using invariant uppercase normalization. Unit suggestions include rolls, bottles, tablets, bags, ml, and litres; any custom label is allowed without conversion. A catalogue item requires no usage quantity. There is no permanent delete operation.

The catalogue persists in its own table through an additive migration. Each read checks current account membership. Writes lock the household and recheck membership inside the transaction, serializing with removal and leaving. Item IDs are looked up only within the current household. All account members can edit; membership powers remain with the existing owner role. Refresh catalogue reloads other members' changes. Controls enable only after the Interactive Server circuit renders; saves and cancelled edits give feedback.

Members can set, change, or clear optional Expected Weekly Usage in the same editor. It is a recurring consumption baseline until explicitly changed, not an actual usage log or a quantity to buy. A blank value means no baseline and clearing it preserves the catalogue item. SQL `decimal(12,4)` stores positive values from 0.0001 to 99,999,999.9999. Server validation rejects zero, negatives, out-of-range amounts, malformed values, exponent/grouping notation, and more than four entered decimal places (including extra trailing zeros), without rounding or losing the entered text. Entry and display use the server's current culture; the form shows a fractional example with the applicable decimal separator.

Changing the unit of an item with a baseline displays a separate, initially empty replacement quantity field. The member must enter a valid replacement in the new unit; both values save in one transaction. No quantity is converted or silently reinterpreted. Cancellation or validation failure leaves both stored values intact. To change unit while removing a baseline, clear and save the baseline first. Items without baselines can change unit without acquiring one.

Every successful edit refreshes an item version. Saves compare the version loaded by the editor while holding the household lock, rejecting stale editors after another member's change and retaining their input for review. Cancel the edit, refresh, and reopen to use the current item. Future item mutations must also refresh this version. The additive migrations preserve existing catalogue entries with absent baselines.

Members can open Planning totals from the catalogue at `/HouseholdItems/Planning`. The Planning Period defaults to one week. Changing it or selecting Calculate expected consumption reloads the current saved baselines after checking current household membership. Each row shows the name, usage unit, Expected Weekly Usage and expected consumption over the selected period. Items without baselines remain in the catalogue and are excluded, with a useful empty state when no baselines exist.

The Planning Period accepts positive whole weeks from 1 through `Int32.MaxValue` (2,147,483,647), an explicitly displayed numeric limit rather than a business maximum. Zero, negatives, fractions, nonnumeric text and overflow receive feedback and clear the previous totals. Calculations use .NET decimal after a household-scoped query; the supported baseline and period limits keep multiplication within decimal range. Totals preserve up to four fractional places without rounding up: 6 rolls over 3 weeks is 18 rolls; 0.25 bottles over 3 weeks is 0.75 bottles. These are expected consumption estimates; the application does not subtract stock, calculate purchase quantities, round to packs or convert units. Archived items are excluded from both the active catalogue and these totals, including recalculation and reload.

Any current household account member can archive an item from its catalogue card. Archived items persist at `/HouseholdItems/Archived`, linked from the active catalogue, with their identity, unit and optional baseline intact. Restore returns them to the active catalogue and planning; absent baselines stay absent, and restored baselines remain editable and clearable. For example, shampoo at 0.25 bottles per week contributes 0.75 bottles over three weeks, nothing while archived, and 0.75 again when restored. Permanent deletion remains outside scope. The additive archive migration defaults existing rows to active.

Archive and restore each recheck membership under the transactional household lock and scope item lookup to the current household. Both compare the displayed item version and rotate it on success. Stale catalogue edits fail even after an archive–restore cycle, without overwriting current names, units or baselines. Already archived/restored actions and stale versions receive refresh guidance. Archived reads and refreshes check current membership, including already-open circuits after access removal. Names remain unique across active and archived items, preserving their identity rather than creating duplicates. A duplicate archived name points to restoration in Archived items.
## Browser verification

The browser test follows real registration, invitation joining, catalogue create/edit/reload, shared editing, isolation, removal, and a retained editor after revocation. It also covers fractional baseline persistence, editing/clearing, quantity validation with retained input, supported endpoints, missing baselines, atomic unit replacement and cancellation, shared 0.25-bottle usage, stale unit editors, and independent baselines in separate households. Planning workflows cover the default/empty state, both calculation examples, the maximum supported weeks, invalid/overflow periods with no misleading totals, current baseline edits/clearing, reload, shared access, household isolation, authentication and an already-open planning session after removal. Archive workflows also cover reload/recalculation exclusion, finding archived items, restoration with and without a baseline, editable restored baselines, sharing, isolated archived reads, stale editors across archival and restoration, repeated/stale archive and restore actions, and revoked archive/restore/read circuits. Assertions observe pages, not database tables. The local runner extends the existing Playwright verification approach and publishes the app to exercise production assets, applies fresh migrations to a uniquely named LocalDB database, uses a random localhost port, and removes only that generated database afterward. It does not load production credentials or target the production database.

Prerequisites: .NET 10 SDK, Windows SQL Server LocalDB (`MSSQLLocalDB`), `sqlcmd`, Microsoft Edge, and Playwright resolvable through Node. For example, install Playwright into ignored scratch tooling with `npm install --prefix .scratch/browser-tooling playwright`, then set `NODE_PATH` to that absolute node_modules directory.

From the repository root, run `node scripts/Test-HouseholdItemsLocal.cjs`. The runner publishes the host itself. Existing `dotnet test` checks remain separate.
